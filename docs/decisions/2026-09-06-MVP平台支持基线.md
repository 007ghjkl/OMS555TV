# 2026-09-06 MVP 平台支持基线

## 背景

Host 采用 C++17、Qt 6、CMake 和 Ninja，代码结构避免依赖非必要的 Windows 专用 API；但 Phase 0～8 的配置、构建、全部 CTest、QSerialPort 通信、UI 与真实 RS485 验收均只在 Windows x64、Qt 6.8.3 和 MSVC 2022 环境完成。PRD 与架构此前未明确“源码具有可移植边界”和“平台已经获得支持证据”的区别。

Phase 9 需要为 README、复现说明和现场演示提供不夸大的平台承诺，因此必须在不虚构 Linux 结果的前提下关闭该未决项。

## 可选方案

### 方案 A：同时声明支持 Windows 与 Linux

- 优点：对潜在使用者覆盖更广，符合 Qt/CMake 的跨平台定位。
- 缺点：当前没有 Linux 配置、构建、CTest、串口枚举、权限和真实 RS485 证据。
- 风险：把设计意图写成已验证事实，首次复现失败时无法定位为代码、工具链还是串口权限问题。

### 方案 B：仅声明 Windows x64 为已验证平台，保留 Linux 可移植边界

- 优点：与现有证据一致；既不承诺未测试平台，也不主动引入不可移植实现。
- 缺点：Linux 使用者需要后续单独完成工具链和串口验证。
- 风险：若 README 省略“当前证据基线”字样，读者可能误解为永久排除其他平台。

### 方案 C：不提供平台支持声明

- 优点：无需维护支持矩阵。
- 缺点：构建和演示入口不明确，不满足 Phase 9 可复现目标。
- 风险：用户可能自行组合未经验证的 Qt、编译器和操作系统版本。

## 决策

采用方案 B。

MVP 对外承诺的已验证 Host 平台为 **Windows x64**，当前完整证据基线为 **Qt 6.8.3、MSVC 2022、CMake 和 Ninja**。这里的版本描述表示现有验证组合，不承诺所有 Windows、Qt 6 或 MSVC 版本均已验证。

源码继续维持 Qt/CMake 的可移植边界，不无理由引入 Windows 专用业务逻辑；但 Linux 在完成独立配置、构建、全部测试、应用启动、串口枚举/权限和真实 Modbus RS485 验证前，不列为已支持平台。

## 原因

1. Phase 0～8 的真实证据全部来自 Windows x64，支持声明必须服从已有证据。
2. Qt/CMake 提供跨平台可能性，但框架能力不能替代本项目的构建和硬件验证。
3. Windows 基线足以满足当前 MVP、简历展示和现场演示目标。
4. 该决策可逆；未来可以通过独立任务增加 Linux 支持，而无需改变现有通信、测试或报告架构。

## 影响

- README、PRD、架构和测试计划统一使用“Windows x64 已验证；Linux 保留可移植边界但未验证”的口径。
- TASK-029 的干净构建和现场演示验收只以 Windows 基线作为必须通过项。
- Linux 不进入当前缺陷统计和 MVP 退出条件；未来验证失败也不能反向修改既有 Windows 结果。
- 若要增加 Linux 支持，必须另立任务，至少覆盖编译器/Qt 版本、全部 CTest、应用启动、串口设备发现与权限、真实 RS485 收发、日志和报告导出。
- Windows 安装包、CI 和多版本兼容矩阵仍不在本决策范围内。
