# TASK-021 Host Phase 7 引导式测试模型与 Schema v3

## 目标

在保持 v1/v2 测试契约兼容的前提下，定义可审计的半自动测试模型、Schema v3、人工动作记录和自动观察判定，使“人工操作硬件、软件采集证据并自动判定”成为严格的数据驱动流程。

## 背景

Phase 6 已完成 20 条真实 RS485 主套件、复合步骤、预期超时、稳定性和自动协议恢复，但现有 Schema/Engine 不支持暂停等待人工动作，也不能记录提示、确认、取消和恢复时间。PRD 与 `PROJECT_SPEC.md` 第 18 节要求半自动测试必须有明确提示、继续/取消操作、软件最终判定，并把人工步骤纳入后续报告。

TASK-020 的自动恢复只证明远端异常后合法请求成功，不能替代物理 RS485 断线与重连。本任务先固化输入、状态和证据契约，后续任务不得在 QWidget 中临时拼接人工流程。

## 范围

- 实现前创建并评审 `specs/host_phase7_guided_test_schema.md`。
- 新增独立 `test-suite-v3.schema.json`；不得原地改变 v1/v2 Schema 语义。
- Loader 同时支持已确认的 v1、v2 和 v3，未知版本继续整体拒绝。
- v3 新增受限 `guided_recovery` 用例类型，至少支持：
  - 人工提示步骤；
  - 明确的继续/确认与取消动作；
  - 自动观察通信中断；
  - 人工重连提示；
  - 自动观察通信恢复；
  - 软件最终 PASS/FAIL/ERROR 判定。
- 定义人工步骤模型：step ID、标题、中文指令、安全提示、允许动作、等待上限和取消后恢复指引。
- 定义观察步骤模型：探测请求、间隔、截止时间、目标结构化结果、连续满足次数和可选业务断言。
- 定义通信中断条件，至少支持连续 `ResponseTimeout`；不得把取消、串口权限、端口消失或任意错误视为成功断线证据。
- 定义恢复条件，至少支持连续合法 0x03 响应和业务断言满足。
- 定义人工动作记录：prompt/step ID、展示时间、动作、确认/取消时间、可选备注和关联运行 ID。
- 定义恢复时间的起点、终点和局限：以用户“已重连”确认为起点，以首个满足恢复条件的响应为终点，同时记录连续成功完成时间。
- 扩展不可变结果模型，使 Phase 8 可直接消费人工动作、观察结果、RequestId/TX/RX/RTT 和自动判定，不重新解释日志文本。
- 添加有效/无效 v3 fixture、中文示例和纯数据模型测试。

## 非范围

- 不实现半自动运行状态机、按钮、对话框或真实 RS485 操作。
- 不实现自动重连、端口重新枚举或隐藏的串口 close/open。
- 不实现 STM32 Reset、传感器断开或人工改变传感器输入用例。
- 不实现 HTML/PDF 报告；只提供后续报告所需的不可变数据。
- 不引入任意脚本、Shell 命令或可执行动作字段。

## 实现门禁

1. Spec 必须先定义 guided case、人工步骤、观察步骤和整套运行的状态机及唯一终态。
2. 用户确认只代表用户声明动作已完成，不得单独作为物理断线或恢复 PASS 证据。
3. 取消、等待超时、观察失败、通信致命错误和用户中止的状态优先级必须固定。
4. 人工等待与观察 deadline 必须有界；不得让 Testing owner 无限占用串口。
5. stale/重复确认必须通过运行 ID、用例 ID、step ID 和一次性 token 拒绝。
6. 取消发生在物理链路可能仍断开时，必须保留明确的恢复接线提示和未恢复状态，不能静默结束。
7. v3 证据模型必须满足 Phase 8 报告需求，但本任务不得提前实现报告模板。

## 实现要求

1. v3 继续采用 UTF-8、`additionalProperties=false` 和全有或全无加载策略。
2. guided 步骤类型、数量、提示长度、等待上限、探测间隔、deadline 和连续次数均必须有明确上限。
3. 正式 RS485 引导用例只允许安全的读探测；写寄存器与人工断线不得组合。
4. 观察条件只依赖结构化通信结果和断言，不匹配诊断文本。
5. 人工动作记录使用 UTC 审计时间，持续时间和 deadline 使用单调时钟。
6. 恢复时间同时记录首个成功和连续成功确认两个口径，UI/报告不得混用。
7. 结果区分 operator cancel、operator timeout、outage not detected、recovery timeout、fatal communication error 和 internal error。
8. v1/v2 加载、执行模型和正式 Phase 6 套件必须保持兼容。

## 验收标准

1. Technical Spec 已评审，提示、确认、取消、观察、计时和结果状态无未决项。
2. Host 全新配置、构建和全部 CTest 通过，无 Phase 5/6 回归。
3. v1/v2 fixture、Phase 5 套件和 Phase 6 两个正式套件保持原加载结果。
4. v3 有效 fixture 覆盖断线提示、连续超时、重连提示、连续成功和自动判定。
5. 未知步骤/动作、缺失恢复指引、非法 deadline/interval、重复 step ID 和不安全写请求均被结构化拒绝。
6. 人工动作与观察结果可完整关联 run/case/step/token 和 RequestId。
7. 恢复时间两种口径通过确定性时钟测试，边界无负值或溢出。
8. stale、重复和跨运行确认均被拒绝且不改变状态。
9. 测试不访问 QWidget、串口或真实硬件。
10. 最终 Review 无必须修复项，允许进入 TASK-022。

## 测试要求

- v1/v2 兼容回归与 v3 Schema/Loader 一致性。
- v3 有效/无效 fixture、步骤顺序、动作 token 和安全字段。
- 结果模型：人工记录、观察证据、恢复时间和错误分类。
- 时间边界：确认、deadline、连续样本和溢出。
- 回归：全部 Host CTest 和应用 smoke test。
