# TASK-019 Host Phase 6 完整自动化套件与 UI 集成

## 目标

基于 TASK-017/018 的 v2 输入与执行能力，建立不少于 20 条具有独立验证目标的完整自动化测试套件，并在现有 Qt 自动化测试页面中完整展示复合步骤、数据一致性和稳定性统计。

## 背景

Phase 5 的 8 条真实 RS485 基础用例只覆盖动态读数、版本、非法地址和单路阈值恢复，不能代表 Phase 6 的功能、协议、边界、数据一致性、自动恢复和稳定性覆盖。现有候选目录共 24 条，其中超时、连续请求、运行时间组合和稳定性此前受 v1 能力限制。

本任务负责把覆盖矩阵落成可重复加载和执行的正式套件，并完成 Fake/offscreen 验证；真实硬件全量结果由 TASK-020 独立验收。

## 范围

- 创建 Phase 6 正式 v2 套件，例如 `testcases/phase6/phase6-rs485-full.json`。
- 正式套件至少包含 20 个唯一、启用且有独立验收目标的用例，最低分类数量为：
  - 功能测试 8 条；
  - 协议测试 4 条；
  - 边界测试 4 条；
  - 数据一致性测试 2 条；
  - 自动恢复测试 1 条；
  - 稳定性测试 1 条。
- Phase 5 用例可在满足最终 Schema、证据和唯一 ID 要求后纳入计数，但不得重复计数或换名复制。
- 覆盖温度/光敏、阈值、告警/设备状态、固件版本、正常读写、非法地址/数据、最小/最大阈值、地址边界、符号与运行时间字序。
- 自动恢复至少验证一次远端协议异常或确定性通信错误后，后续合法请求仍能受控成功；物理拔插/复位留给 Phase 7。
- 稳定性用例至少配置 10 分钟、明确轮询间隔、寄存器范围、最低样本数和允许失败率。
- 对真实硬件不易安全构造的超时或极值，可建立独立 Fake 边界套件；必须在覆盖矩阵中标明环境，不能冒充实机结果。
- 所有写入用例保存原值、独立回读并恢复；恢复失败使套件为 ERROR。
- 更新自动化测试页面，展示 sequence 步骤、当前迭代、进度、聚合统计和证据保留说明。
- 更新 `docs/test_cases.md`，使每个正式 ID 可追溯到需求、环境、预期和套件路径。
- 添加 Loader、Engine、控制器和 offscreen UI 的正式套件自动测试。

## 非范围

- 不执行 TASK-020 的真实 RS485 全量验收或宣称 Phase 6 完成。
- 不实现 Phase 7 人工提示、确认、物理断线、复位或传感器操作。
- 不实现 Phase 8 HTML/PDF 报告。
- 不实现 Raw Frame、CRC 错误注入、0x04、0x10 或自动重连。
- 不为达到数量复制同一请求、同一预期或无业务意义的变体。

## 依赖

- TASK-017 v2 Schema、断言和覆盖矩阵已完成。
- TASK-018 sequence、expect_timeout、数据一致性和 stability 执行能力已完成。
- TASK-016 自动化测试 UI 与真实 RS485 基础套件已完成。
- Firmware 寄存器表与当前真实硬件基线保持不变。

## 实现门禁

1. 正式用例清单必须先评审其独立目的、数据来源、执行环境、安全性和清理方式。
2. “有效用例”必须可加载、可执行、具有明确预期、进入稳定终态并保留证据；disabled、SKIPPED、重复或仅有说明的条目不计数。
3. 实机套件不得依赖不可控环境精确值；动态数据使用合理范围或位掩码，稳定字段才使用精确值。
4. 不得通过写只读地址、越界阈值或复合步骤绕过通信层和 Firmware 的安全边界。
5. Phase 6 自动恢复必须与 Phase 7 物理恢复在文档和 UI 中明确区分。
6. stability 的默认验收时长不得缩短为单元测试时长；CTest 可用虚拟时间，但正式 JSON 保持至少 10 分钟。

## 实现要求

1. 所有正式用例采用稳定 ID、中文名称、category、描述、标签和明确预期。
2. 套件可重复运行；任何阈值写入后都应恢复执行前值，而不是硬编码恢复默认值。
3. 多寄存器动态读取使用逐元素断言，不以多条单读冒充同一块快照测试。
4. 数据一致性至少覆盖 int16 符号/缩放和 uptime 低高字组合，不只检查原始数组长度。
5. 协议用例至少覆盖 0x03、0x06、0x02 和 0x03 异常；预期 timeout 只能在确定性 Fake 环境计入对应覆盖。
6. 自动恢复用例必须在错误后发出新的合法请求，并保存前后 RequestId/TX/RX 和恢复耗时。
7. UI 统计只来自 TestResultManager，不重新计算或解释 Engine 结果。
8. 正式套件及 Fake 脚本在自动测试中逐 ID 核对，防止新增/删除用例后覆盖矩阵失真。
9. 内存摘要与 JSONL 全量证据的界面提示与 Spec 一致。

## 验收标准

1. Host 全新配置、构建和全部 CTest 通过，无 Phase 5 回归。
2. 正式套件至少 20 条有效用例，六类最低数量全部满足且 ID 唯一。
3. Schema Loader、覆盖矩阵、JSON 套件和自动测试中的 ID 集合完全一致。
4. 全套 Fake 执行所有用例均进入明确终态，并覆盖至少一个可控 FAIL、ERROR 和中止测试路径。
5. 所有写入/边界用例的恢复步骤有自动测试，恢复失败能提升为 ERROR。
6. 自动恢复用例证明错误后合法请求可以成功，且没有隐式重连或并发访问。
7. stability 虚拟 10 分钟结果包含样本、成功/失败/超时、失败率和 RTT 统计。
8. UI 可显示复合步骤、稳定性进度和最终汇总，长循环期间保持响应且可中止。
9. `docs/test_cases.md` 不再把正式用例仅标为候选，并明确尚未完成真实 RS485 全量验收。
10. 最终 Review 无必须修复项，允许进入 TASK-020。

## 测试要求

- 套件完整性：数量、唯一 ID、类别、覆盖矩阵和安全清理。
- Fake 全套：成功结果、断言失败、通信错误、timeout、恢复和稳定性。
- UI：加载、选择、长时进度、步骤详情、统计、中止和状态门禁。
- 回归：全部 Host CTest、v1/v2 fixture、Phase 5 套件和 smoke test。
