# TASK-027 Phase 9 工程文档基线与架构图

## 目标

以当前主分支代码、已完成任务和真实验证记录为唯一事实来源，完成核心工程文档的一致性审计，补齐可在 GitHub 直接查看的系统架构图，并明确 MVP 的平台支持口径，为展示素材和最终验收建立可信基线。

## 背景

Phase 0～8 已形成需求、架构、寄存器、测试和缺陷文档，但部分标题、状态和阶段描述仍保留“草案”或旧阶段口径。`PROJECT_SPEC.md` 将 README、架构图、寄存器表、测试计划和 Bug 记录列为 Phase 9 必交付物；PRD 与架构还保留 Windows/Linux 支持范围未决项。工程完善不能只做排版，必须先证明文档与实际代码、测试证据一致。

## 范围

- 创建并维护一份 Phase 9 文档审计清单，至少覆盖 `README.md`、`docs/prd.md`、`docs/architecture.md`、`docs/hardware_baseline.md`、`docs/modbus_register_map.md`、`docs/test_plan.md`、`docs/test_cases.md`、`docs/bug_records.md` 和 Phase 0～8 验证记录。
- 对照 Firmware `register_map`、Host `RegisterMap`/`RegisterCodec` 与正式测试套件，逐项核对寄存器地址、访问属性、缩放、有符号解释、多字顺序、异常响应和当前限制。
- 在 `docs/architecture.md` 中补齐可由 GitHub 原生渲染的 Mermaid 图，至少包含：系统/硬件边界、Host 模块依赖与唯一通信所有权、监控/测试/报告数据流。
- 更新架构状态与各阶段完成事实，明确生产 RS485 与可选 VCP 回归端点、线程边界、状态机、日志证据和报告边界。
- 审计测试计划和测试用例目录，使 Fake、真实 RS485、人工操作、长稳态和未验证工业环境的结论保持分层。
- 审计 `docs/bug_records.md`；只记录有真实复现、根因、修复和回归证据的缺陷，不为展示补造 Bug。
- 形成平台支持决策记录：MVP 的已验证基线为 Windows x64、Qt 6.8.3、MSVC 2022；Linux 只保留可移植边界，除非另有真实构建证据，不声明为已支持平台。
- 同步关闭 PRD 和架构中的平台口径未决项，并为 TASK-028/029 提供稳定引用。

## 非范围

- 不修改 Firmware、Host、Modbus 协议、寄存器语义、测试结果或报告生成行为。
- 不新增 Linux 构建、CI、安装包、Raw Frame、自动重连、PDF 或其他进阶功能。
- 不重新执行真实 RS485、长稳态或人工故障测试来美化既有数据。
- 不删除历史任务、Spec、测试记录或真实失败证据。

## 依赖

- TASK-001～TASK-026 的实现、Spec、验证记录和提交历史。
- `PROJECT_SPEC.md` 第 29、31、32 节及 Phase 9 要求。
- 当前 Firmware/Host 寄存器常量、测试套件和构建基线。

## 实现门禁

1. 所有“已完成”“已验证”“支持”的表述必须能追溯到代码、提交或测试记录。
2. 若代码、寄存器文档和测试资产发生冲突，应停止修改结论、登记冲突并先请求确认，不得选择性覆盖。
3. Mermaid 图只表达已实现结构；规划能力必须显式标注，不得与现状混画。
4. 平台口径采用“已验证支持”与“设计上保留可移植性”两层表达，不把未运行的 Linux 构建写成支持。
5. 缺陷记录必须保留原始量化结果和证据链接，不得为面试效果虚构或篡改。

## 实现要求

1. 审计清单记录文件、核对来源、发现项、处理结果和剩余限制。
2. 架构图中的模块名称、依赖方向、线程所有权和数据模型与当前源码一致。
3. 寄存器表逐项与两端常量进行可重复的人工或脚本核对；脚本如新增，只用于检查，不生成另一份事实源。
4. 测试文档明确区分 30 分钟监控、10 分钟正式稳定性、Fake 虚拟长时、短套件报告和半自动断线恢复。
5. 文档链接使用仓库相对路径，中文为主，术语和版本号统一。
6. ADR 说明 Windows 基线、Linux 边界、选择理由、影响和未来改变条件。

## 验收标准

1. 核心文档审计完成，无无法解释的阶段状态、版本、端口或测试数字冲突。
2. `docs/architecture.md` 至少包含三幅可渲染 Mermaid 图，且与当前实现一致。
3. 寄存器表与 Firmware、Host 和正式测试资产逐项一致；发现差异时已有明确处置记录。
4. 测试计划、测试用例和 Bug 记录均能链接到对应真实证据，未扩大结论边界。
5. 平台支持 ADR 已评审，PRD/架构未决项关闭；README 使用相同口径。
6. Markdown 链接、标题和 Mermaid 语法检查通过。
7. 变更仅限文档及必要的只读校验工具，无生产代码行为变化。
8. 最终 Review 无必须修复项，允许进入 TASK-028。

## 测试要求

- 文档一致性：版本、阶段、任务状态、硬件、串口和测试数字交叉核对。
- 寄存器一致性：Firmware、Host、文档和 JSON 套件的地址/语义核对。
- 图表：在 GitHub 兼容 Mermaid 渲染器中验证语法和可读性。
- 链接：检查全部新增或修改的仓库内链接。
- 范围：确认未修改生产代码、测试结论或原始证据。
