# TASK-006 Host Phase 3 Modbus 后端决策与异步通信规范

## 目标

在实现 Host 生产通信代码之前，完成 Modbus 后端、线程模型、串行请求队列、原始证据和错误模型的架构决策，并输出可直接指导后续实现的 Technical Spec。

## 背景

`TASK-004` 已完成设备模型与寄存器编解码，但当前 `IModbusClient` 只有连接状态接口。PRD 要求打开/关闭串口、0x03、0x06、超时、结构化错误、完整 TX/RX、RTT 和单通道所有权；架构推荐“单通信工作线程 + 串行请求队列”。

Phase 0 技术验证已确认 Qt SerialBus 的公开 Raw API 只暴露 PDU，不能取得完整 RTU ADU，也不能注入错误 CRC。直接选择 Qt SerialBus 或自建 QSerialPort 后端会影响后续监控、测试证据和故障注入能力，因此本任务先做正式决策，不在未确认时写生产后端。

## 范围

- 对照 PRD、架构和 `research/qt_serialbus_raw_frame.md` 复核通信能力矩阵。
- 比较至少两个方案：Qt SerialBus 标准后端与基于 QSerialPort 的受控 RTU 后端。
- 明确普通业务通信与 Raw Frame/错误注入是否使用同一后端。
- 输出 `docs/decisions/2026-09-03-Host-Modbus后端.md`。
- 输出并评审 `specs/host_phase3_modbus_communication.md`。
- 扩展设计层面的 `IModbusClient` 契约，定义连接配置、异步读写、请求 ID、响应、取消和状态通知。
- 定义单通信工作线程、串行请求队列及对象线程归属。
- 定义 TX/RX、时间戳、RTT、功能码、地址、CRC 结果和错误上下文的证据模型。
- 定义串口、超时、CRC、协议异常、参数、取消和内部状态错误的结构化分类。
- 定义监控与测试模式交接通信所有权的接口边界。
- 设计 Fake/Mock 行为，使后续通信调度可在无硬件环境测试。
- 通过最小验证代码或公开 API 证据确认关键假设，但不提交生产通信实现。

## 非范围

- 不实现完整 QSerialPort 或 Qt SerialBus 生产后端。
- 不连接真实串口，不与 STM32 联调。
- 不实现监控轮询、参数配置 UI、通信调试 UI、TestEngine 或报告。
- 不实现 Firmware 或 `TASK-002` RS485 硬件迁移。
- 不擅自增加 0x04、0x10 或新的公共寄存器。

## 必须评审的方案

### 方案 A：Qt SerialBus 作为主后端

- 优点：标准功能实现量较少，Qt 生命周期和异常响应已有封装。
- 缺点：公开 API 不提供完整 RTU ADU，无法直接满足完整 TX/RX 证据和错误 CRC 注入。
- 必须说明：若保留此方案，如何补齐证据和 Raw Frame 能力，以及是否会形成两套协议路径。

### 方案 B：QSerialPort 受控 RTU 后端

- 优点：可以控制完整 ADU、CRC、帧间隔、原始证据和故障注入，通信与测试共用同一路径。
- 缺点：需要自行实现和维护 Master 状态机、超时、粘包/分包、异常响应和线程安全。
- 必须说明：如何复用测试向量降低协议重复实现风险。

## 决策门禁

1. ADR 必须给出推荐方案、理由、已知风险、回退方案和对后续任务的影响。
2. 如果推荐方案会改变当前架构草案，应先由用户确认，再把架构文档标记为已决策。
3. Technical Spec 必须在生产后端实现任务创建前完成评审。
4. 不得使用 Qt 私有头文件或未验证的内部 API 规避 Raw 能力限制。
5. 不得为了错误注入在监控和 TestEngine 中复制第二套不受控 Modbus 实现。

## Technical Spec 最低内容

- 串口配置模型及其合法性约束。
- `IModbusClient` 异步方法、输入、输出和生命周期。
- 请求 ID、队列状态、在途请求和完成结果模型。
- 工作线程启动、关闭、断开、重连和对象销毁顺序。
- 单请求超时、取消、停止接收新请求和受控排空行为。
- RTU ADU/PDU、CRC、TX/RX 和 RTT 的证据边界。
- Modbus 异常响应与本地通信错误的区分。
- 监控、测试和手动调试之间的通信所有权交接。
- Fake Client 的确定性响应、超时、错误和取消脚本。
- 单元测试、集成测试、线程测试和真实硬件测试策略。

## 验收标准

1. ADR 对两个方案进行可核验比较，并给出单一推荐方案。
2. 推荐方案能够逐项覆盖 PRD 的打开、关闭、配置、0x03、0x06、超时、错误、完整 TX/RX 和 RTT 要求；不能覆盖的项目必须明确列为缺口。
3. Technical Spec 明确保证同一串口同一时刻最多一个在途请求。
4. UI 主线程不承担阻塞通信，任何工作线程均不直接操作 QWidget。
5. 连接关闭、请求取消、超时和对象销毁不存在未定义的线程归属或悬空回调。
6. 结果模型可以携带请求 ID、时间戳、完整证据、RTT 和结构化错误。
7. 监控与测试模式的所有权交接与架构状态机一致。
8. Fake/Mock 设计足以验证队列顺序、超时、异常、取消和模式切换。
9. 规范明确哪些验证不需要硬件，哪些验证必须等待 `TASK-005` 或 `TASK-002`。
10. 本任务只产生决策、规范和必要的最小验证，不提交生产通信后端。
